## パスタを折るな。責務を分けろ

こんにちは、黒パグです。

雑な要件を入力して「🍝 パスタを折って生成」を押すと、イタリア人の情緒を犠牲にしながら、保守可能な実装指示へ変換するアプリを作りました。

名前は **PASTA BREAKER**。

リセットすると、こう聞かれます。

> Spezzare la pasta?! Vuoi morire?  
> パスタを折るだと？ お前、死にたいのか？

画面の最下部では、カルボナーラの作り方がイタリア語で永久に流れます。もちろん生クリームは禁止です。

ここまでは完全にネタです。

ところが、アプリの中身は思ったより真面目です。むしろ、ネタの皮を被せなければ少し説教臭くなる程度には、生成AI時代の実装事故を正面から扱っています。

この記事では、PASTA BREAKERを題材に、次の話をします。

- 曖昧な自然言語を、そのままコードへ流さない方法
- 「分割しただけ」の設計と、変更理由で分けた設計の違い
- AIエージェントへ渡す完了条件と境界条件
- iPad・埋め込みブラウザで発生した実際のリンク障害
- テストが壊れたとき、製品コードとテスト模型をどう切り分けるか

パスタは折りますが、話は折りません。

## なぜスパゲッティコードは生まれるのか

スパゲッティコードという言葉は、複雑に絡み合い、変更の影響範囲が読めないコードを指す比喩として使われます。

ただし、原因を「下手なプログラマが長い関数を書いたから」で済ませると、ほぼ何も改善しません。

実務で絡まるのは、コードより先に**要求**です。

たとえば、次の依頼を考えます。

```text
ログインできて、売上も見られるSaaSを全部いい感じに作る。
本番DBっぽいやつで。今日中。
```

一見すると短く、AIへ渡しやすいプロンプトです。しかし、実装上の未確定事項は山ほどあります。

- 誰がログインするのか
- 認証方式は何か
- テナント分離は必要か
- 売上の定義は何か
- 集計期間とタイムゾーンは何か
- 金額の丸め方は何か
- データの作成元はどこか
- 閲覧権限と更新権限は同じか
- 失敗時に何を表示し、何を記録するか
- どの状態をもって完成とするか

AIは、空白を埋めることが得意です。だから危険です。

不足を不足のまま報告せず、もっともらしい仮定で埋め、画面とAPIとDBを一気に作る。動くものは出てきますが、その瞬間に大量の暗黙仕様が誕生します。

つまり、スパゲッティコードの入口は巨大関数ではありません。

**実装を始める前に、決めるべきことと仮定してよいことを分けなかった時点**です。

## PASTA BREAKERが最初に行うこと

PASTA BREAKERは、入力された要求を即座にコードへ変換しません。先に、実装担当へ渡す指示の形へ整えます。

中心に置いた規律は、次の5つです。

1. 不足要件を分類する
2. 責務を変更理由で分ける
3. 境界を明示する
4. 完了条件を観測可能にする
5. 未確認を成功として報告しない

### 1. 不足要件を二種類に分ける

不足要件は、すべて質問すればよいわけではありません。質問を増やしすぎると、実装は一歩も進みません。

そこで、次の二種類へ分けます。

```text
A. 実装を止める不足
   誤るとデータ破壊、権限事故、大幅な手戻りにつながるもの

B. 安全に仮定できる不足
   仮定を記録し、後から局所的に交換できるもの
```

認証方式、外部決済、本番データの扱いはAになりやすい。一方、初期表示の並び順や仮のページサイズは、交換点を閉じ込められるならBとして進められます。

重要なのは質問数ではなく、**誤った仮定の爆発半径**です。

### 2. 責務を「ファイルサイズ」ではなく「変更理由」で分ける

よくある改善は、800行のファイルを200行ずつ4つへ分割することです。

これは整理にはなりますが、設計にならない場合があります。4ファイルが同じ共有状態へ触り、1つの仕様変更で全部修正するなら、結合度はほぼ変わっていません。

PASTA BREAKERでは、少なくとも次の責務を意識させます。

```text
UI             入力、表示、ユーザー操作
Domain         業務ルール、計算、状態遷移
Data Access    保存、取得、トランザクション
External I/O   API、ファイル、通知、外部サービス
```

分割の基準は「短くなるか」ではなく、**別々の理由で変更されるか**です。

たとえば、売上集計の丸め規則が変わったとき、画面コンポーネントやDB接続処理まで同時に編集するなら境界が弱い。ドメイン処理だけを交換できるなら、変更の局所性があります。

### 3. データ境界・エラー境界・権限境界を列挙する

AIへ「堅牢に作って」と頼んでも、堅牢性は実装できません。抽象語だからです。

代わりに境界を指定します。

```text
データ境界: 外部入力が内部の型へ変換される場所
エラー境界: 失敗を捕捉し、分類し、通知する場所
権限境界: 誰が何を読めて、何を変更できるかを判定する場所
```

この三つが見えると、入力検証、例外処理、認可処理の置き場所が決まります。

逆に境界が曖昧だと、各コンポーネントが独自に検証し、各関数が独自に例外を握り潰し、画面の表示条件だけで権限を制御する、といった事故が起きます。

### 4. 完了条件を観測可能にする

「本番レベル」「いい感じ」「高品質」は、完了条件ではありません。

完了条件は、人間またはテストが確認できる形にします。

```text
- 未ログインで保護URLへアクセスするとログイン画面へ遷移する
- 権限のないユーザーへ売上明細を返さない
- データ0件では空状態を表示する
- API失敗時は成功表示にせず、再試行可能なエラーを出す
- 集計結果と元データの合計が指定した丸め規則で一致する
```

ここまで書けば、実装担当が人間でもAIでも、確認対象が揃います。

### 5. 未確認を成功に変換しない

生成AIによる実装で厄介なのは、コードの誤りだけではありません。

```text
実装済み
ビルド成功
単体テスト成功
ブラウザ確認済み
本番反映済み
```

これらは別の状態です。

ビルドできたからブラウザで動くとは限らず、テストが通ったから本番へ反映されたとも限りません。反対に、テストが落ちたから製品コードが壊れているとも限りません。

PASTA BREAKERは、提出物として「実際に確認した結果」と「未確認事項」を分けて報告するよう求めます。地味ですが、エージェント運用ではかなり重要です。

## 「最小構成」と「雑な一枚岩」は違う

PASTA BREAKERは、最小構成での実装を促します。

ここでいう最小構成は、すべてを1ファイルへ詰め込む意味ではありません。

目的は、最初から巨大な汎用基盤を作ることでも、未来の全要件へ備えることでもありません。最初の価値を縦に貫く、小さな動作単位を完成させることです。

たとえば売上閲覧機能なら、次の一本を先に通します。

```text
認証済みユーザー
  ↓
閲覧権限の判定
  ↓
売上データの取得
  ↓
集計規則の適用
  ↓
成功・空・失敗の表示
  ↓
監査可能な記録
```

この流れに必要なものだけを実装し、交換点と観測点を残します。

過剰設計を避けることと、境界を捨てることは別です。

## ネタアプリで本当に起きた障害

ここからは、PASTA BREAKERを無駄なもの研究所の本館へ追加したときに起きた、実際のデバッグです。

本館には複数の展示があります。多くは本館と同じサイト内に置かれていますが、PASTA BREAKERだけは独立したSiteとして公開されていました。

最初のリンク実装は単純でした。

```tsx
<a href={exhibit.href}>
  研究成果を無駄に体験する ↗
</a>
```

デスクトップブラウザだけを想定すれば、普通に見えます。

しかし、iPadアプリ内の埋め込み表示では、別オリジンへの同一画面遷移が期待どおり動きませんでした。利用者から見れば、「パスタを押せない」です。

原因はパスタ生成処理ではありません。本館からパスタへ移動する**ナビゲーション境界**でした。

修正では、外部URLだけを新しいタブで開き、内部展示の遷移は維持しました。

```tsx
function ExhibitCard({ exhibit }: { exhibit: Exhibit }) {
  const isExternal = exhibit.href.startsWith("http");

  return (
    <a
      href={exhibit.href}
      target={isExternal ? "_blank" : undefined}
      rel={isExternal ? "noreferrer" : undefined}
      aria-label={`${exhibit.title}を体験する${
        isExternal ? "（新しいタブで開く）" : ""
      }`}
    >
      研究成果を無駄に体験する ↗
    </a>
  );
}
```

この修正の要点は、単に`target="_blank"`を足したことではありません。

- 内部リンクと外部リンクを区別した
- 既存の内部遷移を変更しなかった
- 新しいタブで開くことをアクセシブルネームへ含めた
- 外部ページへ現在ページの参照情報を渡さないよう`rel`を設定した

つまり、変更範囲を境界へ閉じ込めています。

「ボタンが押せない」という症状だけを見て、PASTA BREAKER本体のJavaScriptを変更していたら、無関係なコードを壊していた可能性があります。

ネタアプリでも、障害切り分けはネタでは済みません。

## テストが落ちた。だが製品コードは壊れていなかった

本館の回帰確認では、15件中1件のテストが失敗しました。

対象は、画像研究室のコピー・フォールバック選択・ダウンロード機能を、簡易DOM模型で検証するテストです。

エラーは次の種類でした。

```text
TypeError: Cannot set properties of undefined (setting 'appName')
```

アプリには、アクセス解析スクリプトを動的に読み込む処理が追加されていました。

```js
const analyticsLoader = document.createElement("script");
analyticsLoader.src = "/analytics.js";
analyticsLoader.dataset.appName = "image-research";
document.head.appendChild(analyticsLoader);
```

実ブラウザで`document.createElement("script")`が返す要素には、`dataset`があります。`document.head`にも`appendChild`があります。

ところが、テスト用のNode模型には、その二つがありませんでした。

つまり壊れたのは製品機能ではなく、**ブラウザの契約を不完全に再現したテストダブル**です。

修正前の模型は、概ね次の状態でした。

```js
class Node {
  constructor(tag) {
    this.tag = tag;
    this.children = [];
    this.events = {};
  }
}
```

必要な契約だけを追加します。

```js
class Node {
  constructor(tag) {
    this.tag = tag;
    this.children = [];
    this.events = {};
    this.dataset = {};
  }

  appendChild(node) {
    this.children.push(node);
    return node;
  }
}

const documentMock = {
  // 既存の最小実装
  head: new Node("head"),
};
```

修正後は15件すべて成功しました。さらに11個のHTML展示についてローカル資産の参照切れを確認し、主要JavaScriptの構文検査も通しています。

ここで重要なのは、「テストが落ちたから本体を直す」という短絡を避けたことです。

テスト失敗時には、少なくとも次の四つを分けます。

```text
1. 製品コードの欠陥
2. テストコードの欠陥
3. テストデータ・fixtureの欠陥
4. 実行環境または依存関係の欠陥
```

テストは仕様の証拠になり得ますが、テスト自体もソフトウェアです。当然、古くなり、壊れ、誤判定します。

## iPad対応はレスポンシブCSSだけでは終わらない

モバイル対応というと、画面幅とタップ領域の話になりがちです。もちろん、それも必要です。

しかし、iPadやアプリ内ブラウザでは、さらに実行コンテキストを見る必要があります。

- 通常のSafariか、アプリ内WebViewか
- ポップアップや新規タブが許可されるか
- クリップボードAPIが使えるか
- `dialog.showModal()`が期待どおり動くか
- ファイルダウンロードが許可されるか
- 別オリジンへの遷移がどの画面で開くか
- ユーザー操作に同期した処理か

たとえばコピー機能では、`navigator.clipboard.writeText()`が拒否される環境があります。そのため画像研究室では、失敗時にテキストエリアを開いて全文選択する経路を持たせています。

```js
try {
  await navigator.clipboard.writeText(prompt);
  announce("コピーしました");
} catch {
  details.open = true;
  field.focus();
  field.select();
  field.setSelectionRange(0, field.value.length);
  announce("全文を選択しました。コピー操作で取得してください");
}
```

重要なのは、API対応表を眺めるだけではなく、**拒否されたときの利用経路を設計すること**です。

「対応ブラウザでは使える」と「その埋め込み環境で成功する」は同義ではありません。

## AIへ渡すプロンプトを、仕様書の代わりにしない

PASTA BREAKERが生成するものは、完成した仕様書ではありません。

ここは誤解しやすい部分です。

生成される指示は、実装前の論点を露出させ、AIが勝手に暗黙仕様を増やすのを抑えるための**作業契約**です。

したがって、プロンプトを長くすれば安全になるわけではありません。

必要なのは、次の対応関係です。

| 曖昧な要求 | 実装可能な表現 |
|---|---|
| いい感じに | 判断軸と優先順位を示す |
| 本番レベル | 脅威、負荷、復旧、監視条件を示す |
| エラーに強く | 対象エラーと利用者への応答を示す |
| 拡張しやすく | 予想される変更点と交換境界を示す |
| テストも書いて | 守る振る舞いと失敗条件を示す |

プロンプトの価値は文字数ではなく、**判断を再現できるか**で決まります。

## エージェント実装で最低限残したい出力

AIエージェントへ実装を任せる場合、コードだけを提出させると状況が読めません。

PASTA BREAKERでは、次の出力を要求します。

```text
1. 5〜10行の実装計画
2. 変更するファイル構成
3. 動作するコード
4. 実行・確認方法
5. 実際に確認した結果
6. 未確認事項
7. 既知の技術的負債
8. 次に壊れそうな場所
```

これは報告書を長くするためではありません。

人間が見るべき場所を絞るためです。

特に「次に壊れそうな場所」は有効です。実装した本人、またはエージェント自身に、変更の弱点を言語化させられます。

もちろん、申告が正しい保証はありません。だから実際の差分、テスト、ログ、画面確認と突き合わせます。

Human on the loopは、Approveボタンを押す係ではありません。

## ネタにすると、設計原則を触れる形にできる

責務分離、境界条件、観測可能性、失敗状態、回帰テスト。

単語だけを並べると、正しいけれど読み飛ばされやすい話です。

そこでパスタを折りました。

「巨大な万能関数を作るな」と表示するだけなら、誰も触りません。「NONNAが泣いている」と表示されれば、とりあえず危険度スライダーを動かします。

ネタUIは、技術を薄めるためではなく、触る入口を作るために使えます。

ただし、ネタで隠してよいのは堅さであって、穴ではありません。

- ボタンは押せるか
- 失敗時に戻れるか
- 外部遷移は環境差を考慮したか
- コピーできない場合の代替経路はあるか
- テストは製品の現在の契約を再現しているか
- 確認していないことを確認済みと書いていないか

ここを落とすと、「スパゲッティコード防止アプリが押せない」という、ネタとしては満点、製品としては失格の状態になります。

実際、一度なりました。

## まとめ

PASTA BREAKERは、パスタを折ってイタリア人を怒らせるアプリです。

同時に、生成AIへ雑な要求を丸投げする前に、次の点を固定するための小さな設計ツールでもあります。

- 止めるべき不足と、安全に仮定できる不足を分ける
- 責務を変更理由で分離する
- データ・エラー・権限の境界を示す
- 完了条件を観測可能にする
- 実装済み、テスト済み、確認済み、公開済みを混同しない
- 実行環境の差に対して代替経路を持つ
- テスト失敗時は本体とテスト模型を切り分ける

生成AIがコードを書く速度は上がりました。

だからこそ、人間が曖昧な要求を投げてから後悔する速度も上がっています。

まず要件を折る。責務を分ける。境界を見る。確認結果を正直に書く。

パスタは鍋へ。

コードは保守可能な場所へ。

それではまた🐾
